01

Skill 體系建置

方法論 · 品質機制
問題
  • 十餘個前端專案，技術棧從傳統多頁應用到現代 SSR 框架
  • 跨專案開發最大成本不是寫程式，是搞懂「這件事在這專案怎麼做」
  • AI agent 在不熟的專案裡給出的答案不能直接用
做了什麼
  • 建立可被 AI agent 自動載入的 Skill 體系
  • 定義團隊產出 Skill 的五支標準流程
  • 設計出題驗收機制，確保 Skill 真的能帶讀者找到答案

體系分層

平台既有 執行環境層 決定何時載入哪支 Skill。不可修改，只能配合其限制設計。
我主導 流程層 — 五支標準作業流程 規範「怎麼產出一支 Skill」。輸入研究題目，輸出通過驗收的 Skill。
我參與 內容層 — 各專案與跨專案主題 Skill 其中多支由其他同事依上述流程產出。

我的主要價值不在寫了幾支 Skill，而在定義別人怎麼寫。體系中有數支完全由他人產出，正是流程可被沿用的證明。

五支流程各司其職

建立從零研究新主題
→
更新局部補寫
→
重整只動結構
→
去重跨文件收斂
→
驗收出題回歸測試

拆成五支而非一支，因為維護型改動與從零建置的風險完全不同

  • 早期只有「建立」一支，每次小修正都得整份重寫，順手改錯的機率高
  • 拆開後「更新」只准動指定段落，把風險限制在必要範圍
  • 「建立」流程中設兩道檢查點，必須由人確認才往下，避免方向錯了還一路做到底
02

Chrome 擴充套件：在別人的網站上呈現自家內容

Vue 3 · Manifest V3
問題
  • 業務人員在外部平台看物件時，想知道自家資料庫有沒有相關資訊
  • 得另開分頁、複製地址、手動搜尋，來回切換又容易漏
這個套件做什麼
  • 偵測使用者正在看哪個物件頁，自動比對自家資料庫
  • 在瀏覽器側邊欄即時呈現結果，與對方頁面並排
  • 登入沿用自家網站帳號，不需另建帳號系統

整體流程

使用者
在外部平台瀏覽物件頁 切換分頁、換頁或重新整理
↓瀏覽器事件通知
背景服務
判斷目前網址是否為支援的物件頁 不支援則顯示說明畫面，流程結束
↓
背景服務
檢查登入狀態 讀取自家網站 Cookie ——瀏覽器開放套件讀取其權限範圍內的 Cookie
未登入 導向自家網站登入頁，走完既有流程即可，不需在套件裡另登一次
已登入 帶著 Cookie 向自家換發存取憑證，存入套件儲存空間
↓
背景服務
呼叫自家 API 比對資料 由背景服務發出請求：它擁有套件宣告的跨網域權限，不受所在頁面的同源限制
↓寫入套件儲存空間
側邊欄
讀取並呈現比對結果 由瀏覽器提供的獨立區域，與對方頁面並排；不屬於對方網頁，因此不受其封鎖或樣式影響
↓使用者觸發動作時
側邊欄
以訊息機制把請求送回背景服務 畫面層不直接對外要資料，一律經由背景服務；監聽器須明確宣告非同步回覆，否則通道會在結果回來前關閉

設計取捨

為什麼從「注入對方頁面」改成「並排側邊欄」？

原本把介面注入對方頁面，視覺上能融入對方版面，但對方偵測得到也擋得掉——後來確實被封鎖了。改用瀏覽器提供的側邊欄後，介面不再屬於對方網頁，對方碰不到；代價是無法與對方版面融合。改變呈現載體，而非在被封鎖的路徑上繞過。

03

週報自動化工具

Python · 排程 · AI 協作
問題
  • 每週回想「上週做了什麼」花時間又容易漏
  • 資料其實都在版本控制系統裡，只是散在各專案
這支工具做什麼
  • 每週一定時自動撈上週的 PR 與推分支紀錄
  • 整理成週報草稿：去重、推測狀態、翻成白話
  • 停下等我確認與補充，回「送出」才貼到當週同步議題
程式 撈取活動上週 PR 與推分支
→
AI 整理草稿去重、推測狀態、白話化
→
人 停下確認核對並補「本週」
→
程式 送出貼到當週議題

確定性的工作交給程式，需要判斷的交給 AI，有代價的動作交給人
